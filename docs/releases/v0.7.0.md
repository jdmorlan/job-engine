# v0.7.0 — a job that retries, history that ends, and helpers to import

Three things a scheduler needs before it is one, and none of them was here:
a job that fails twice at 3am now tries again on its own, history stops
accumulating forever, and a TypeScript job can `import je from "je"` without a
package to install.

## Read this before upgrading

**Retention deletes history, and it starts at 4am the day after you upgrade.**
Runs, their captured output and the timeline are kept for thirty days. If this
deployment has been running longer than that, the first sweep removes what is
older — permanently, and without asking.

Two things it will never remove, whatever their age:

- The run that set a job's **current cursor**. Losing that would make "what did
  this job last process?" unanswerable, which is the question D14 exists for.
- A run the **timeline still describes**, because events are kept at least as
  long as runs and `je why` reads through them.

If any of your jobs produce output you need to keep, say so in the job file
before the first sweep — it exempts that job's logs, and its runs with them:

```yaml
keep_logs: forever
```

And what goes is counted, so a trimmed history never reads like a short one:

```console
$ je runs house/chatty
no runs within the keep period; 412 older run(s) have been removed by
retention. je explain system/retention
```

The periods are arguments in the built-in `system/retention` job, so
`je explain system/retention` is the answer to "what is my retention policy?"
They are not yet configurable without rebuilding, which is the one obvious
limitation of shipping them this way.

**`retrying` is a new run status.** Anything reading `je runs` output or the
API's `status` field sees a value it has not seen before. It is not terminal: a
run in it has failed an attempt and is waiting for the next one.

**Coming from v0.4.x or earlier?** Read [v0.5.0's notes](v0.5.0.md) and
[v0.6.0's](v0.6.0.md) first. Between them, TLS became mandatory, workers must
enroll, and definitions moved out of `~/.je/jobs` into a repository you own.
This release does not repeat any of it.

## Retries (D7)

A job that is safe to repeat says so. Nothing retries by default, because the
engine cannot know whether running your job twice sends one email or two:

```yaml
retry:
  max_attempts: 3       # counting the first; 1 (the default) means no retry
  backoff: exponential  # or fixed
  initial_delay: 10s
  max_delay: 5m
```

Attempts belong to the run, so a job that fails twice and succeeds on the third
try is **one** successful run with three attempts:

```console
$ je run house/sync
attempt 1 talking to the flaky API
connection refused
je: attempt 1 of 3 failed: exited 7 -- retrying in 10s (2 attempts left)
...
ok  run 12 succeeded in 32.4s
    attempts
      1  failed     jay              22ms  exited 7
      2  failed     automatic retry  32ms  exited 7
      3  succeeded  automatic retry  31ms  -
```

Failures and timeouts retry. Interruptions do not — `on_interrupt` already
decides those — and neither does a **lost** run, because a worker that stopped
answering may still be running your job, and retrying could double-fire work
that is still in flight.

`je retry <run>` adds an attempt by hand. It is not `je run`: a retry is another
go at the same intent with the same input cursor, while `je run` is a new run
with a fresh cursor read. A manual retry ignores `max_attempts`, and the history
keeps the two apart — which is what makes "did a human have to intervene?" a
question you can answer.

A run waiting out a backoff sits in `je waiting` with the clock it is waiting
on, and survives a restart: the wait is a column, not a timer.

## Helpers you can import (D21)

A job that declares its language gets the helpers for it, where we ship them:

```typescript
import je from "je";                       // written by the worker, not installed

const readings = await fetchReadings(je.state.since);
je.setState({ since: readings.at(-1).ts });
je.emit("weather.ingested", { count: readings.length });
je.output({ rows: readings.length });
```

There is no package to install and no version to match: the shim is materialised
by the same binary that runs your job, so there is no version pair that can be
wrong. It is sugar over the protocol and may never be more than that — a job in
a language we ship no shim for does exactly as much through the files it writes.

TypeScript only for now, on purpose. A shim nobody uses rots quietly, so the
next one arrives when a real job wants it.

**A job declaring a language no longer needs a manifest.** A one-file script
with nothing to install is an ordinary job; a tree that *has* a `package.json`
or a `pyproject.toml` it cannot install from is still an error.

## Trying a job while you write it

```console
$ je try ingest
je: preparing typescript in ~/code/weather-jobs
ingested 2 readings

ok  ingest would have succeeded
    cursor  would move to {"since":"2026-09-04T13:00:00Z"}
    output  {"rows":2}
    emit    weather.ingested {"count":2}
```

`je try` reads the definition out of the directory you are standing in, prepares
the tree exactly as a worker would — your dependencies, your helpers — runs the
command, and shows what the engine **would** have committed. Nothing is
recorded: no run, no history, no cursor movement, no control plane.

Its checks are the engine's own code rather than a second opinion, which matters
most for the failure it exists to catch early:

```console
$ je try sloppy
all done!

x  the job exited 0 but broke the protocol:
   job state must be a JSON object, got [
```

In a real run that is a failed run and a message you have to go and find.

`--state '{"since":"..."}'` gives it a starting cursor and `--event '{...}'` a
triggering payload.

## The engine's own work is a job

Retention is not a loop inside the control plane. It is `system/retention`, an
ordinary job in a built-in source, dispatched to a worker like any other, with
runs and logs and a visible failure:

```console
$ je jobs --all
JOB               STATUS  COMMAND                                             FILE
system/retention  ok      je retention sweep --runs 30d --logs 30d --events…  jobs/retention.yaml
```

It is hidden from `je jobs` by default — the "is everything OK?" screen should
not be mostly housekeeping — and its source cannot be unregistered.

## Also

- **`je new --language python` writes `language: python`**, which it had been
  refusing to do. Both halves of that field are built now.
- **`--data-dir ./relative` is resolved to an absolute path.** It was stored
  verbatim, which broke anything running from a different directory.
- **The logs database can give space back.** Deleting rows never shrank the
  file; it does now, reclaimed in bounded chunks rather than one long lock. A
  database created before this release is converted once, and says so.
