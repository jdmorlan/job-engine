# v0.6.0 — definitions live in a repository

`je` stopped having a jobs directory. Definitions live in a git repository you
own and reach the engine as a registered source, which is what makes a job's
code, its scripts and its encrypted secrets travel to whichever worker runs it.

That is the breaking change, and everything else in this release either follows
from it or is a consequence of the same idea: the engine reads what you wrote,
and owns nothing you authored.

## Read this before upgrading

**Your existing jobs will stop loading.** The built-in `local` source — the
`~/.je/jobs` directory — is gone, along with directory sources entirely. On
first start, migration `0011` tombstones the jobs, chains and routes that came
from one.

**Your history is kept.** Runs, cursors and events survive, because removing a
definition has never removed its history (D19). `je runs` still shows what ran
last month under the name it ran under.

So the upgrade is: put your job files in a repository, and register it.

```console
$ cd ~/.je/jobs                       # or wherever yours live
$ git init && git add -A && git commit -m "jobs"
$ gh repo create my-jobs --private --source=. --push

$ je upgrade                          # binary, then restart what runs here
$ je source add house <you>/my-jobs
```

Job names then carry their source — `house/water-plants` rather than
`water-plants` — which is the one thing to fix in any script that names a job.

**Coming from v0.4.x?** Read [v0.5.0's notes](v0.5.0.md) too: that release made
TLS mandatory and requires workers to enroll, and this one does not repeat it.

**Directory sources are gone, not deprecated.** A job whose code sat on the
control plane's disk could only ever run on a worker that shared that disk, so
the kind was already broken the moment there were two machines — which is the
shape the container and cluster deployments are for. Registering a path is now
an error that says so.

## What is new

**A getting-started guide.** [GETTING-STARTED.md](../../GETTING-STARTED.md) —
fifteen minutes from nothing to a job of your own, with no concepts up front.
The README keeps the design and gains a one-page "how it works" at the top.

**Runtimes.** A job declares its language and the worker installs its
dependencies from the repository's own lockfile before running it:

```yaml
language: typescript
command: ["tsx", "ingest.ts"]
```

Installed once per tree, keyed on `(language, tool version, lockfile)`, so a
commit that did not touch dependencies installs nothing. `je worker runtime
install python` fetches a toolchain — verified against a published checksum, the
same rule `je upgrade` applies to itself, and nothing is installed that cannot
be checked. A worker advertises which languages it can prepare, so a job whose
language nothing serves is queued and visible in `je waiting` rather than
dispatched to a machine that would fail it.

**Fan-in.** A step can wait for several things at once:

```yaml
steps:
  - on:
      all_of:
        - { event: run.succeeded, where: { job: house/extract-weather } }
        - { event: run.succeeded, where: { job: house/extract-power } }
      within: 6h
    run: rollup
```

`within:` is required — a fan-in with no window fires on events days apart and
looks like nothing is wrong. Partial satisfaction is durable, so a pair that
lands either side of a laptop sleeping still completes, and `je waiting` shows
exactly which condition is outstanding and when what it already has expires.

**Reach a worker on another machine.** `je workers restart <name>` and
`je workers upgrade <name>`. Both are requests: the worker acts at its next
heartbeat, after finishing what it is running, so a restart never costs an
in-flight job. `upgrade` replaces that worker's own binary first.

**`je reset`** tears down everything on this machine — containers, services,
volumes, databases, certificates, caches — for when a clean slate is the fastest
way forward. It only removes what *this* data directory owns, and says what it
left alone and why.

**Commands that only work on one machine now say so.** `je help` marks them with
a `*`. The distinction is invisible until it bites: `je runs` works identically
against a control plane in a cluster, and `je control-plane remove` does not —
it removes a service *here* while the cluster carries on.

**The CLI stopped sending you to Docker.** A CLI on the host of a containerised
control plane finds it, takes the certificate it needs out of the container by
itself, and a worker started there enrolls with nothing pasted. `je upgrade`
restarts containers as well as services. The exception is a deployment you drive
with `docker compose`, which is your file and stays yours.

## Smaller things

- `je new` writes into the directory you are standing in, and `--script` became
  `--language` (the old spelling still works and says so).
- `je init` no longer tells you to register a directory, which had stopped
  working.
- `--github-api` on `control-plane run` and `quickstart`, for GitHub Enterprise.
- `jobs_dir` is gone from `je status` and from the health endpoint, and
  `JE_JOBS_DIR` is gone with it.
- Three migrations: `0011` removes the local source, `0012` records a worker's
  runtimes, `0013` its pending directive.

## Known gaps, named rather than hidden

- **`trigger.expired`** — fan-in's "the thing I was waiting for never came"
  event — is not built. It needs a sweep rather than arrival-time evaluation.
- **Retries, the container executor and retention** are still not built.
- **Two secret stores** remain, on purpose: the control plane's own, which it
  can read and redact, and the repository's, which it cannot.
- **The compose worker is `FROM scratch`**, so it can run only `/je` — there is
  no `/bin/sh`, and therefore none of the demo jobs.
