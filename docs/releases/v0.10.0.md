# v0.10.0 — `je up`, and output you can scan

Getting started meant `je quickstart`: a control plane and a worker in your
terminal, which is not how anybody actually runs this. `je up` brings up the
whole engine the way it is meant to run, in one command.

```console
$ je up

control plane  registered as a service  127.0.0.1:7620
worker         registered as a service  default
web            running as a container   http://127.0.0.1:7621

  open http://127.0.0.1:7621         history, chains and schedules in a browser
  je status                          is it up, and is anything attached
  je source add <name> <owner/repo>  point it at your jobs
  je down                            stop all of it; data and history stay
```

The engine also stopped printing everything at the same weight. Every view is
coloured now — a failed run is red before you have read the word, a value you
set in a job file stands out from the eleven defaults around it, and the only
cyan on the screen is something you can type.

## Read this before upgrading

**`je quickstart` is gone. It is `je up --foreground`.** The old behaviour is
unchanged and still one command; it is a flag now rather than a command of its
own, because a quick start that teaches you a deployment you would never
actually use is a detour rather than a start. Anything scripted against
`je quickstart` needs the new spelling.

**`--print` used to perform native installs.** `je control-plane install
--native --print` and `je worker join --print` accepted the flag, ignored it,
and registered a real service. Only the container path honoured it. If you ever
ran one of those expecting nothing to happen, check `je control-plane status`
and `je worker status` — something may be registered that you did not mean to
register.

**If you have a native control plane, `je up` keeps it native.** It does not
move an existing deployment into a container, for the reason under `je up`
below. Nothing about upgrading changes shape.

No schema change. An existing deployment upgrades in place.

## `je up`

Three components, each in the shape it should actually run in:

| | shape | why |
|---|---|---|
| control plane | container (native if one is already here) | it owns a database and should survive a reboot without a terminal staying open |
| worker | native service | the published image is `FROM scratch`, so a container worker runs only jobs that need nothing but themselves |
| web client | container | stateless, and there is nothing to gain by treating it differently |

None of that is new capability — `je control-plane install --docker`, `je worker
join` and `je web start` all existed. What did not exist was the one command
that composes them, so the fastest path into the engine was the one that taught
you the least.

**It is safe to run again.** Anything already up is reported and left alone, so
it is also how you bring back the piece that died:

```console
$ je up
control plane  already running          127.0.0.1:7620
worker         already attached         default
web            already running          http://127.0.0.1:7621
```

**An engine that is already here keeps the shape it has.** A containerised
control plane keeps its database in a named volume, so moving an existing native
deployment into a container would not migrate it — it would start an empty one
beside it, with every run and cursor still on disk and none of it in the engine
you are now talking to. So the container default applies to a machine with no
engine on it; a machine that already has one is not asking a question about
defaults. Asking for the move explicitly is refused rather than done quietly:

```console
$ je up --docker
je up: there is already a control plane's data in /Users/you/.je, and a containerised one
would not use it -- it keeps its database in a named volume, so this
would start an empty engine beside your history rather than moving it.

  je up                    keep the deployment you have
  je reset                 move that data aside first, and start fresh in a container

Nothing has been changed.
```

**`je down` is the inverse**, and keeps everything that matters:

```console
$ je down
web            stopped                  container removed
worker         stopped                  unregistered
control plane  stopped                  unregistered

Left alone: your data directory, job definitions, run history and secrets.
  /Users/you/.je

  je up   brings it back
```

That gap was real: until now the only whole-deployment teardown was `je reset`,
which destroys your history. `je reset` is still the one that does that, and it
still says so and asks first.

**When it cannot do the default, it says which default it took.** A machine
without Docker — or a development build, which has no published image — gets a
native control plane and a sentence explaining why, rather than a failure:

```console
$ je up
je: this is a dev build, which has no published image, so the control plane
    goes in as a native service.
    `je up --docker` moves it once that is sorted.
```

`--foreground`, `--native`, `--docker`, `--no-web`, `--addr`, `--web-addr`,
`--labels` and `--print` are all there. And `je up --print` now genuinely prints
and does nothing — all three components, as commands you could have typed.

## Output that has a foreground

The engine has always tried to say the right thing. It said all of it in the
same weight, which on a dense view is close to saying nothing: `je explain`
prints twelve values, and the two you actually set looked exactly like the ten
you inherited. They do not any more.

```console
$ je explain demo/demo-counter
demo/demo-counter  Counter
demo-counter/job.yaml

  command               /bin/sh counter.sh  (job.yaml:4)
  workdir               demo-counter        (default)
  timeout               1h                  (default)
  state.primary_cursor  count               (job.yaml:9)
```

Declared values stay bright; inherited ones recede. The same rule runs
throughout: a state word is coloured, a command you can type is cyan and nothing
else is, and everything a table needs but you are not scanning for — timestamps,
file paths, provenance — steps back.

`je help` was thirty-one commands in one alphabetical list, where `chain`,
`chains` and `control-plane` sat together because of a letter they share. It is
grouped now, ordered by when you meet them: start here, write jobs, see what
happened, make something happen, definitions and secrets, run the engine
yourself.

**Colour is never the only signal.** A failed run says "failed" in red, never
only in red. It is off when stdout is not a terminal, so piped and redirected
output is unchanged, and `NO_COLOR` and `TERM=dumb` are honoured. `--color=auto|always|never`
overrides all of it.

The alignment underneath is new too. `text/tabwriter` measures a cell with
`len()`, so a coloured cell is several bytes wider than it looks and every
column drifts — correct in a test, visibly crooked on screen. Tables now measure
display width, which is also why no line ends in trailing whitespace any more.

## Four bugs that only a real deployment finds

Building `je up` meant running the containerised paths end to end for the first
time, and they did not work. Each of these was reachable before this release;
making a container the default is what turned them from corner cases into the
common path.

- **The web client could not verify the control plane, and crash-looped.** Its
  container had no volume and therefore no copy of the authority, so since D25
  made HTTPS the only transport, `je web start` produced a container that
  restarted forever. The authority is mounted in read-only now.
- **A native control plane's certificate did not cover `host.docker.internal`.**
  With that fixed, the web container started, served its own assets, and got a
  proxy error on every API call — the certificate is valid for the machine's own
  name and `localhost`, and not for the name a container reaches its host by.
  It is issued for that name too now, on the same reasoning as the hostname
  beside it: cheaper than a flag nobody knows to pass.
- **Nothing checked that the web client worked.** `docker run` returning was
  treated as success, which is how the two bugs above stayed invisible. It is
  verified through `/v1/health` rather than at `/`, because the client serves
  its own assets out of the binary — `/` returns 200 from a container that
  cannot reach the control plane at all.
- **A stale certificate authority won over a live one.** On a machine that had
  ever run a native control plane, installing a containerised one left the old
  CA on disk and preferred it, so every command failed against a control plane
  that was up and answering, naming an authority the reader has never heard of.
  The endpoint file already records which shape is in use; it now decides which
  authority is right, and a containerised install takes its CA out of the
  container before anything tries to verify.

## Also

- **`--print` is honoured on every path it is accepted on** (see above). The
  command it prints for a native install now comes from the same function the
  service manager runs, rather than a second hand-rolled copy that could drift.
- **A half-finished `je up` exits 3, not 1.** A control plane that registered and
  then did not answer is something to look at, not a failure to bring anything
  up — and it now says so once instead of printing three accounts of the same
  event.
- **`je init` and `je new` next-steps, and the `je demo` tour**, are tables of
  commands rather than paragraphs to read.
- **D29 is on the record**, not built: `je build`, which would generate a worker
  image from a jobs repository using what D28's toolchain table already knows.
  The open questions are in `PROPOSAL.md`, including the one that decides
  whether it is coherent at all — whether such an image carries your code or
  only the environment it needs.
