# v0.9.0 — `je dev`, and secrets that land where you put them

Writing a job used to mean pushing it to GitHub to find out whether it worked.
`je dev` runs it straight from the directory you are standing in — as a real
run, with real logs, events and cursor.

```console
$ je dev water-plants
je: ~/code/my-jobs -- 2 job(s), 1 chain(s)
watering 3 zones since 2026-09-04T13:00:00Z

ok  run 6 succeeded in 124ms
    cursor  since  2026-09-04T13:00:00Z -> 2026-09-05T00:36:21Z  (v6)
    emitted plants.watered (event 32)
```

An edit takes effect on the next command. No commit, no push, no sync.

## Read this before upgrading

**If you set a secret with `je secret set --source`, set it again.** That command
wrote into the control plane's *cache* rather than your checkout — it printed
that path, said it was readable, and told you to commit a file that was not in
your repository. Anything set that way is gone with the cache. It writes to your
working copy now:

```console
$ je secret set --source house API_TOKEN
created ~/code/my-jobs/secrets.enc.yaml, readable by this machine
set API_TOKEN in house
left uncommitted: secrets.enc.yaml
```

**`je try` is gone, replaced by `je dev`.** It shipped in v0.7.0 and lasted two
releases. See below for why.

There is one schema change (migration `0017`, which adds the `dev` source kind).
An existing deployment upgrades in place; verified by building a v0.8.0
deployment with history and starting v0.9.0 on it.

## `je dev`

Every source is a repository (D27), which is right for what production runs from
and left authoring with no answer: a job you are *writing* had to be committed
and pushed before the engine could run it, every time.

`je dev` points the control plane on your machine at a directory. **Everything
after that is the ordinary path** — same dispatch, same worker, same
environment, same secrets decrypted from your own `secrets.enc.yaml`, same logs
and events and cursor. So your job appears in the views you would use in
production, and a chain fires from your working copy:

```console
$ je runs
2    dev/water-plants  succeeded  19:32:09  64ms
1    dev/water-plants  succeeded  19:31:59  153ms

$ je chain dev/watering
  trigger  dev/water-plants  run 4  succeeded in 180ms
  step 1   dev/log-watering  run 5  succeeded in 8ms  on plants.watered
```

Jobs from it are named `dev/<job>`, so their history and their cursor are their
own — a job you are writing cannot touch the record of the same job served from
a repository, and every run says it was a development run by its name alone.

It needs a control plane that can read the directory, which means one on this
machine (`je quickstart`), and it says so plainly if it cannot.

### Why `je try` went

`je try` ran the job *itself*: a harness in the CLI that prepared the tree, built
an environment, called the executor, and printed what would have been committed.
It wrote nothing, so it looked like it escaped D20/C11's rule against a second
executor.

It did not. It reimplemented four things the worker already did — dependency
preparation, the environment, the executor call, the log sink — and the
environment had drifted before the release that shipped it was a day old: it
passed your whole shell through, where a real run gets `PATH`, `HOME`, `TZ` and
its declared secrets. A job reading an ambient variable passed under `je try` and
failed under `je run`, which is the exact failure it existed to prevent.

`je dev` cannot drift, because there is nothing to drift from.

## Secrets in a repository actually work now

Three things in that path were broken, and the first is why the other two never
mattered:

- **`je secret set --source` wrote to the cache**, as above. The cause was a D27
  leftover: a field documented as "where a directory source reads from" — a kind
  D27 deleted — was still populated, with the cache path, for every repository
  source.
- **`je secret list --source x` ignored `--source`**, reporting the control
  plane's own store, so it said `no secrets set` to somebody who had just set one
  in `x`. It lists the source's now — names and readers, never values — and names
  the revision it is describing, because a secret in your checkout is invisible
  to the control plane until it is pushed and synced.
- **You found out you needed a key by failing.** `je secret set --source` makes
  one if there is none, and says so, instead of telling you to run
  `je worker keygen`.

Which means the declared-secret loop works before anything is pushed:

```console
$ je dev water-plants
je dev: job dev/water-plants is misconfigured: secret not set: WEATHER_API_KEY
        (set it with: je secret set --source dev WEATHER_API_KEY)

$ echo "sk-live-..." | je secret set --source dev WEATHER_API_KEY
$ je dev water-plants
api key: ***
```

The worker decrypts it from the tree and redacts it back out of the job's own
logs, exactly as it does in production.

## Also

- **A job whose definition is gone says so.** Running one reported its stale
  config error, or "is disabled" — the row is kept so its history stays readable,
  not so its last known problem can be reported forever.
- **A secret's suggestion names the source it belongs in**, rather than pointing
  at the control plane's store for a job that came from a repository.
