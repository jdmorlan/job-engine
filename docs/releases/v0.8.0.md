# v0.8.0 — a job is a folder

A definition at the top level and its code in a shared `scripts/` directory
reads badly the moment there is more than one job: the two halves of one thing
sit in different places, and `scripts/` grows a file per job while pairing with
none of them.

```
my-jobs/
├── water-plants/
│   ├── job.yaml          <- the folder names the job
│   ├── water-plants.mjs
│   └── zones.json        <- and whatever else it needs
├── weather-ingest/
│   ├── job.yaml
│   └── ingest.ts
├── chains/
│   └── morning.yaml
└── package.json          <- dependencies stay the repository's
```

A job is one thing to read, move or delete, and it **runs in its own folder** —
so its command names the files next to it, with no path prefix.

## Nothing you have stops working

**Your existing repositories load unchanged.** A flat `<name>.yaml` is still a
job, for one that has nothing to keep beside it, and a `scripts/` directory is
still just a directory. The two forms coexist in the same repository:

```console
$ je jobs
JOB               STATUS  COMMAND                        FILE
mixed/legacy-job  ok      /bin/sh scripts/legacy-job.sh  legacy-job.yaml
mixed/new-job     ok      /bin/sh run.sh                 new-job/job.yaml
```

There is no migration and nothing to convert. Move a job into a folder when you
next touch it, or never.

**What changed is what `je new` writes.** It scaffolds the folder now:

```console
$ je new water-plants --language javascript
wrote water-plants/job.yaml
wrote water-plants/water-plants.mjs
wrote node_modules/je
```

There is no schema change in this release, so upgrading is `je upgrade` and
nothing else.

## Why one level, and not nesting

Loading was deliberately non-recursive, because arbitrary nesting makes a job's
name ambiguous — is it `etl/weather` or `weather`? That rule is intact. A
directory whose *name is the job's name* has exactly the property a file's name
had, and both forms are one level deep.

A directory with no `job.yaml` is simply not a job, so there is no list of
directories to ignore: `chains/`, `node_modules/` and anything else you keep
beside your work are excluded by the same rule rather than by name. A folder
that *has* one and cannot be a job name is an error saying so, because it is a
job somebody wrote and skipping it quietly would be worse.

`je explain` renders where a job runs, like every other value it did not have to
be told:

```console
  command  node water-plants.mjs  (job.yaml:5)
  workdir  water-plants           (default)
```

## `je new` can scaffold the languages that have helpers

`language: typescript` shipped in v0.7.0 with a shim to import, and `je new
--language` offered `sh` and `python` — so the language with the best experience
was the one you could not scaffold.

Both are there now, and they are two different jobs. **JavaScript** runs on what
is already installed. **TypeScript** cannot — `tsx` comes from the tree's own
dependencies — so that scaffold also writes the `package.json` declaring it,
never overwriting one that exists, and prints `pnpm install` as the step before
`je try`.

## The shim ships its own types

`import je from "je"` gave an editor nothing: no autocomplete, and under
`strict` an error on the import itself.

The types live in the package the worker writes, not in a declaration file
scaffolded into your repository — a copy in your repo is a second thing to keep
in step across versions, which is the version pair this design exists not to
have. Checked with a real `tsc`, including that it catches what it should:

```
'je.lastSuccessAt' is possibly 'null'.
Property 'nonsense' does not exist on type 'Je'.
```

`je new` writes the shim as it scaffolds, so your editor knows about `je` before
the first run rather than after it.

## Also

- **`je init` writes a `.gitignore` that covers what running a job leaves
  behind.** It used to say "nothing here is generated", which stopped being true
  when the worker started preparing trees — `je try` installs your dependencies
  and writes the helpers into the tree it is standing in. Your lockfile is
  deliberately not ignored: that is the file the worker installs from.
- **`je init` no longer tells you to `cd .`** when you are already there.
- **The demo repository is converted**, since an example in a layout the tool no
  longer scaffolds is the documentation and the tool disagreeing.
