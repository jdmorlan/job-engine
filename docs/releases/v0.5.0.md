# v0.5.0 — the trust boundary is the certificate

A worker used to be whatever name it claimed, over a plaintext connection on a
network you were asked to trust. It is now an identity this control plane
issued, on a transport where both ends are proved. That is the whole of D25, and
it is why this release breaks things.

## Read this before upgrading

**Upgrading the control plane means restarting its workers.** There is no
plaintext listener any more and no flag that brings one back. A `je` from
before this release cannot talk to a control plane after it — it will say so
plainly rather than failing with a TLS handshake error, but it will not work.

The order that costs the least downtime:

1. Upgrade and restart the control plane. It issues itself a certificate
   authority on start; nothing to configure.
2. Restart each worker. One on the control plane's own machine enrolls itself
   with nothing pasted. One anywhere else needs an identity — see below.
3. Upgrade the CLI anywhere you run it.

**Workers on other machines must enroll.** They previously registered by
claiming a name, which no longer exists as a path:

```console
$ je enroll buildbox --labels linux        # on the control plane
token    Cg2Mq-cHkyFaXKHeUk...
worker   buildbox
labels   linux

On that machine:
  je worker run --token Cg2Mq-... --addr control-plane:7620 --ca-pin 6254837...
```

The fingerprint is checked *before* the token is sent, because a token is a
bearer credential: whoever receives it becomes that worker.

**One schema migration**, `0010`, adding `age_recipient` to the workers table.
It runs on start and needs nothing from you.

## What changed

**HTTPS, always, from an authority the control plane owns.** It issues itself a
server certificate and issues every worker one at enrollment — no public CA, no
domain to own, and nothing to renew by hand. A worker replaces its own
certificate on the heartbeat while the current one is still valid, so 24-hour
certificates cost nobody any attention. `--tls` is gone rather than defaulted to
true: a flag that can only be passed one way is not a choice, it is a thing to
get wrong.

**A person can have a certificate too.** `je enroll <name> --client`, redeemed
with `je identity join`, and `je run` is then attributed to somebody rather than
to whatever the request body claimed. `je events` grew an ACTOR column so the
attribution is actually visible.

**Issuing your first client identity changes the deployment**, and the command
says so before you redeem the token: from then on, every request that *changes*
something must present a certificate — `je run`, `je secret set`, `je source
add`, and minting further identities. Reading is untouched. Before that first
client exists there is nobody to be, so writes stay open; this is armed by the
deployment's own state rather than by a setting, because a setting can be true
while no certificate exists, and that is the state where nothing works.

**Secrets that the control plane cannot read.** `je secret set --source X NAME`
encrypts a value into source X's repository instead of the control plane's
store. The file is SOPS-shaped — names cleartext, values encrypted — so a
declared-but-missing secret is still a load-time error rather than a 3am exit
code, and the worker decrypts it and redacts it from log lines *before they
cross the network*. It edits your checkout and offers to commit, because under
D23 granting access should be a diff somebody reviews.

**Recipients are machines, named.** `je secret recipients add --source X
buildbox` resolves a name to the age key that identity registered over its own
certificate. A pasted key is a string nobody checked; a name is a statement
about an identity this control plane issued. Pasting still works and now says
plainly that nothing verified it.

**A worker can run code it cannot see.** A job from a repository source now
fetches its tree from the control plane, keyed by commit, so D20's remote
workers and D22's git sources compose. Before this, a repository job on a worker
that did not share the control plane's disk simply failed.

**Version coherence (D24).** Workers report their version, `je workers` marks
any that disagree with the control plane, and a stale worker is refused work
rather than only refused registration (C10).

## Smaller things

- `docker compose up -d` brings up an mTLS deployment whose worker enrolls
  itself; the bootstrap material is its own volume, so a worker does not mount
  the databases or the secret store.
- Clock skew is compared at enrollment against the server's `Date` header and
  refused past two minutes with both times printed — an expired-certificate
  error is usually two clocks disagreeing.
- `je quickstart --tls` is gone because there is nothing to opt into.
- The spelling is `enroll`, not `enrol`.

## Known seams, named rather than hidden

- **There are two secret stores.** The control plane's own (`je secret set`,
  which it can read and therefore redact) and the repository's (`je secret set
  --source`, which it cannot). That is deliberate, and the README says so.
- **The compose worker is `FROM scratch`**, so it can run only `/je` — there is
  no `/bin/sh`, and therefore none of the demo jobs. `docker compose up -d`
  runs the engine's own work, not yours.
